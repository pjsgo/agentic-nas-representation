# 아키텍처 복원 방법

이 프로젝트에서 복원은 논문·공식 코드에서 확인한 계산을 YAML로 표현하고, 그 표현으로 만든 코드가 선언한 범위의 계산과 계약을 구현하는지 확인하는 작업입니다. 아래는 실제 연구 기록에서 공통적으로 사용한 방법을 요약한 것이며, 모든 실험이 동일한 프롬프트·검사기·입력으로 수행됐다는 뜻은 아닙니다.

## 1. 무엇을 복원하는가

전체 모델 또는 특징을 보존한 block/core를 대상으로 삼습니다. 논문·공식 구현의 버전과 핵심 계산을 확인하고, 포함할 계산과 제외할 계산을 먼저 구분합니다. 해당 아키텍처를 구별하는 계산을 제거한 일반 연산만으로 복원을 완료했다고 판단하지 않습니다.

예를 들어 Mamba-2의 SSD core를 복원했다는 것은 chunk 내부·간 계산과 경계 상태 전달을 확인했다는 뜻입니다. 주변 입력 projection, convolution, gating까지 포함한 전체 Mamba-2를 복원했다는 뜻은 아닙니다. 외부에서 제공하는 입력·파라미터·초기 상태와 내부에서 계산하는 부분의 경계도 명시합니다.

아키텍처별 README와 복원 YAML에서 사용 범위를 확인하고, `provenance.json`에서 코드 출처와 확인 범위를 읽습니다. 논문·공식 코드 근거는 해당 자료의 출처 기록을 따릅니다.

## 2. LLM에 무엇을 제공하는가

| 제공하는 정보 | 역할 |
|---|---|
| 복원 YAML | 연산·연결·파라미터·반복·상태·입출력 정의 |
| 표현 및 연산 해석 규칙 | YAML에 쓰인 연산과 연결의 정확한 의미 |
| 대상별 구현 계약 | 생성자, 파라미터 전달, 입력 포트, 출력 순서와 상태 반환 |
| 응답 형식 | 코드, 진입점, 부품 대응과 불명확한 부분을 구분해 반환 |

공통 요청 원칙은 다음과 같습니다. 이 목록은 실제 프롬프트의 요약이며 원문 그대로의 인용은 아닙니다.

- 제공된 YAML과 해석 규칙을 따르고, 아키텍처 이름이나 익숙한 모델 구조로 누락된 계산을 보충하지 않습니다.
- 필요한 계산이 정의되지 않았다면 불명확한 부분을 보고합니다.
- 원본 아키텍처 코드·독립 참조 코드·평가 입력값·기대 출력·숨겨진 검사 내용을 복원 요청의 정답 자료로 제공하지 않습니다.
- 명시된 계산·공유·상태 계약을 보존하는 범위에서 변수명, 클래스 구성과 구현 방식을 선택할 수 있습니다.
- 선언된 범위 밖의 주변 계층, 학습 기능이나 초기 상태를 임의로 추가하지 않습니다.

연구자가 YAML과 참조를 작성할 때 논문·공식 코드를 확인하는 단계와, LLM이 제공받은 표현으로 코드를 생성하는 단계는 구분합니다. 원본 클래스 구조나 모든 내부 변수의 일치 자체를 복원의 목표로 삼지는 않습니다.

공통 원칙은 유지했지만 대상별 생성자·입출력·파라미터 주입 계약은 달랐습니다. H3처럼 후속 요청에서 인터페이스와 허용되는 구현 방식을 명확히 한 사례도 있습니다. 생성 모델과 설정은 각 `provenance.json`의 `generation` 항목에서 확인합니다. 모델명과 temperature만 같다고 완전히 같은 실험 조건은 아닙니다.

## 3. 무엇과 비교하는가

생성 코드는 같은 입력·파라미터·초기 상태·실행 모드에서 독립 참조와 비교합니다. 참조는 후보를 호출하거나 후보의 계산 함수를 공유하는 자기 비교가 되지 않도록 구성합니다. 논문·공식 연산을 따르는 별도 구현, 다른 라이브러리의 수식 구현, recurrence와 convolution·행렬식처럼 다른 계산 경로 등을 대상에 맞게 사용합니다.

독립 참조와 일치했다는 사실만으로 충분하지는 않습니다. YAML과 후보가 해당 아키텍처의 핵심 계산을 보존하는지도 확인합니다. 참조와 후보가 동일한 잘못된 가정을 사용할 가능성은 수치 일치만으로 배제할 수 없으므로 출처와 범위 확인을 함께 수행합니다.

LLM 생성에 앞서 연구용 실현기로 YAML을 실행한 경우에도, 그 실현기의 성공을 LLM 생성 코드의 성공으로 대신하지 않습니다. 두 코드의 출처와 확인 결과를 구분합니다.

## 4. 어떤 기준으로 완료를 판단하는가

코드가 실행되거나 출력 shape가 맞는 것만으로는 충분하지 않습니다. 선언된 범위에 필요한 다음 항목을 함께 확인합니다.

| 확인 항목 | 보는 내용 |
|---|---|
| 핵심 계산 | 특징적인 연산·연결·반복·갱신 순서가 보존되는가 |
| 출력 | 독립 참조와 허용 오차 안에서 일치하며 출력 구조·shape·dtype가 맞는가 |
| 파라미터·자원 | 필요한 값·shape·공유·등록·변경 여부가 계약에 맞는가 |
| 상태 | 초기 상태 반영, 갱신·반환, 필요한 경우 연속 호출과 구간 분할의 의미가 맞는가 |

대표 입력에는 대상에 맞게 길이·배치 변화, 0이 아닌 초기 상태, mask 또는 메모리 조건 등을 사용합니다. 모든 아키텍처에 모든 검사를 동일하게 적용하는 것은 아닙니다. 사례 수, dtype, 허용 오차와 확인 항목은 대상별 평가 근거에 따릅니다.

`PASS_WITHIN_DECLARED_SCOPE` 같은 표시는 명시한 범위와 평가 기준에서 확인했다는 뜻입니다. 서로 다른 시기의 실험을 하나의 동일한 엄격 검사로 통과시켰다는 의미는 아닙니다. 모델 이름만으로 전체 기능을 완료한 것으로 해석하지 않습니다.

## 5. 실패·후속 요청·수정은 어떻게 구분하는가

생성 원본과 평가 기록을 보존하고, 수정이 필요한 경우 수정본과 변경 이유를 구분합니다. 공개 폴더의 최종 구현이 수정본이면 `candidate_origin`과 출처 기록에서 이를 표시합니다.

- **생성 원본 확인:** 계산 코드를 수정하지 않은 상태에서 해당 범위를 확인했습니다. 이것만으로 최초 시도 성공을 뜻하지는 않습니다.
- **명확화·후속 요청:** 코드가 나오지 않았거나 계약을 명확히 해야 했던 이력은 별도로 남깁니다. 뒤의 성공으로 앞의 시도를 성공 처리하지 않습니다.
- **수정 후 확인:** 생성 코드의 오류를 수정해 확인한 결과입니다. 원본 성공과 구분합니다.
- **범위 제한:** 지원하지 않는 기능은 제외·미해결 항목에 기록합니다. 범위 제한이나 명세 확장으로 과거 실패를 소급해 성공으로 바꾸지 않습니다.

응답을 감싼 Markdown 제거 같은 형식 처리는 계산 코드 수정과 구분합니다. 평가 연결을 위한 파라미터 주입·포트 대응도 누락된 계산을 몰래 보충하는 수단으로 사용하지 않습니다. 개별 시도와 수정의 상세 근거는 연구 기록에서 관리합니다.

## 6. 이 결과가 보장하지 않는 것

작은 사례에서의 계산·계약 확인은 모든 입력에 대한 수학적 증명, 전체 모델의 학습·gradient 동등성, 논문 품질·속도·메모리 성능의 재현을 뜻하지 않습니다. 공통 표현 스키마 전체에 대한 인증도 별개입니다.

관계 YAML의 작성과 부품 매핑 역시 아키텍처의 수치 검증이나 실행 가능한 모델 변환을 대신하지 않습니다. 관계의 확인 범위는 [관계 안내](genealogy-guide.md)를 따릅니다.

이 저장소는 복원 YAML·최종 코드·해석 명세·출처와 결과 범위를 읽고 활용하기 위한 자료입니다. 모든 요청 원문, fixture와 검사기를 포함한 완전한 실험 재실행 묶음은 아닙니다. 정확한 생성 실험을 반복하려면 당시 프롬프트·메시지 순서·모델 및 실행 설정이, 동일한 판정을 반복하려면 참조·입력 생성 규칙·허용 오차·검사기가 추가로 필요합니다. 같은 설정의 재생성이 같은 코드나 결과를 보장하지는 않습니다.
