# 자료 업데이트

개인 저장소는 `architectures/`, `relations/`, `docs/`로 구성합니다. 다른 사람의 폴더에 대한 공동 작업용 연결이 필요하면 별도로 명시하고, 개인 배포에는 포함하지 않습니다.

- 아키텍처 추가 또는 계산 수정: 해당 폴더의 YAML, 최종 구현, 사용 계약, 출처와 `architectures/catalog.json`을 갱신합니다.
- 관계 추가 또는 매핑 수정: 관계 YAML과 `relations/catalog.yaml`을 갱신하고 양쪽 부품 ID를 확인합니다.
- 공통 해석 규칙 변경: `docs/`에서 버전을 구분하고 영향을 받는 YAML의 참조를 갱신합니다.
- 설명과 예시 개선: `docs/`와 해당 아키텍처 README를 수정합니다.

복원 범위를 제한한 경우 해당 자료에 포함 및 제외, 미해결 부분을 기록합니다. 기존 명세로 그 내용을 표현할 수 없다면 명세를 확장합니다. 생성 원본과 수정본의 판정은 구분합니다.

공개 자료에는 사용과 해석에 필요한 정보만 둡니다. 원본 프롬프트, API 응답, 실험 로그, fixture, 상세 평가 보고서, 과거 구현 사본은 연구 작업 공간에서 관리합니다. README에는 세션 진행 상황이나 작업 계획을 적지 않습니다.

설명문에는 중간점을 사용하지 않습니다. 항목은 쉼표로 구분하거나 접속사를 넣어 자연스러운 문장으로 작성합니다.

## 목록과 배포의 일관성

아키텍처는 `architectures/catalog.json`을 기준으로 `architectures/README.md`의 기존 표에 이름순으로 추가합니다. 차수별 통합 섹션, 별도 추가 목록이나 세션 진행 기록을 덧붙이지 않습니다. 개인 저장소의 첫 화면에는 프로젝트 소개, 폴더 안내와 같은 아키텍처 표를 둡니다. 관계가 참조하는 계산 부품은 해당 아키텍처의 기존 YAML과 구현에 통합합니다. 관계 번호별 별도 구현 폴더를 만들지 않습니다. 새 부품의 작성 출처와 검증은 해당 아키텍처 provenance에 기록합니다. 관계는 기존 관계 목록과 전체 관계도, 양쪽 아키텍처의 관련 관계 목록을 함께 갱신합니다. 표시 이름은 카탈로그의 title을 기준으로 표, 개별 문서 제목, 관계 목록과 관계도에서 통일합니다. 검증 날짜와 수정 이력은 각 아키텍처의 provenance에 보존합니다.

개인 저장소 루트와 공유 저장소 `JunseoPark/`의 프로젝트 자료를 동일하게 유지합니다. 게시 요청 시 양쪽 `main`의 반영 여부를 확인하며, 작업 브랜치 푸시만으로 게시 완료라고 보고하지 않습니다. 공유 저장소의 다른 사람 폴더와 최상위 안내는 별도 요청 없이 수정하지 않습니다. 원격 보호 규칙 때문에 직접 반영할 수 없으면 필요한 병합 절차를 명시합니다.

## 공개 문서와 연구 기록의 구분

공개 파일은 내용과 용도로 이름을 정합니다. 내부 작업 차수, 담당자 기호, 세션명을 파일명이나 목록의 분류로 쓰지 않습니다. 현재 범위는 `reconstruction-status.md`, 개별 생성 결과와 실패, 수정, 평가 조건은 각 아키텍처의 `provenance.json`에 기록합니다. 검증 기록에는 날짜, 대상, 실행 또는 기존 결과 재사용 여부, 판정 범위를 명시하며 과거 건수를 현재 검증 결과로 취급하지 않습니다.

정리 전에 중요한 정보의 보존 위치를 정합니다. 출처, 실험 조건, 실패와 수정 이유, 수치 결과, 제약은 유지하고 작업 배정과 진행 메모는 연구 작업 공간에서 관리합니다. 과거 스냅샷을 공개 문서에서 제외할 때는 원본을 연구 작업 공간에 보존하고 Git 이력도 유지합니다. 근거를 가리키는 실제 연구 경로는 내부 차수명을 포함해도 추적성을 위해 변경하지 않습니다.
